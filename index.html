05 Validation framework

I built a validation pipeline, then validated the validator.

An independent project: a parallelized Python pipeline that generates futures trading strategies from Sierra Chart one-minute data, backtests them, and runs five stress tests on each. Before building on its results, I conducted an in-depth review of my own pipeline, tracing every reported number back to the code and the result files. Version two is designed around what that analysis found.

What I built

Data
Sierra Chart one-minute bars for MNQ and M2K micro futures, with strategies on 5-minute to 1-hour timeframes

3 stop multiples × 3 reward-to-risk ratios × signal confluence groups of up to four legs (934,909 candidates × 9 on NQ)
Stress tests
Including a 10,000-iteration regime Monte Carlo in two passes and transaction-cost stress at 2×, 5× and 10×

My analysis

Checking that every test can fail

A test is only informative if some outcome can fail it. Pass A of the Monte Carlo shuffled trades within regime blocks, but reordering trades never changes their total, so its result was fixed by construction: always 0% or 100% profitable.

Checking invariants across modules

A 95th-percentile Monte Carlo drawdown built from a strategy's own trades should never be smaller than the drawdown actually observed. Share of result rows that broke that rule:

Traced to MNQ: backtest dollar figures computed at the full-size NQ rate of $20 per point while the stress tests used the micro rate of $2, a roughly tenfold mismatch.

Traced to M2K: backtest metrics and Monte Carlo trade logs produced by different simulations.

What else my analysis found

  • Time windowsThe six-window check ran inside the same 12 months used for selection, so it measured consistency, not out-of-sample performance.
  • Held-out dataVersion one produced no out-of-sample results.
  • Paper-trading logs58 of 121 records had corrupted timestamps and impossible hold times, so the logs reflect an engine bug rather than the strategies.
  • True trial countOn the order of 106 to 107 simulations per instrument, the number any significance test has to account for.

What version two is designed around

  1. A trial registryEvery simulation is recorded, so the Deflated Sharpe Ratio is computed against the true number of trials.
  2. A held-out periodData that strategy selection never sees, reserved for final evaluation.
  3. One contract specificationShared by every module, so dollar figures cannot diverge between stages.
  4. Automatic invariant checksRules like the drawdown check run on every pass, so impossible results are caught before they are reported.

06 Research interests

The questions my own analysis raised.

Reviewing my pipeline in depth sharpened what I find most interesting about quantitative research. None of these questions are specific to markets. They apply to any analysis built on large searches, simulation or raw instrument data.

From my own analysisThe research question

Selection and evaluation

Keeping the data used to choose a model separate from the data used to judge it.

Held-out evaluation

How to design evaluation so that a reported result reflects data that played no part in choosing the model.

Search at scale

A pipeline exploring on the order of 106 to 107 combinations per instrument.

Multiple comparisons

How to judge significance when the best result comes out of a very large search.

Test design

Confirming that each stress test can actually distinguish a strong result from a weak one.

Validating the validator

How to verify that a statistical test is sensitive to the failure it is meant to detect.

Consistency across stages

One shared specification for units and parameters across every module.

Invariant checks

Building automatic checks into a pipeline that flag results that should be impossible.

Data integrity

Validating raw records before computing anything from them.

Integrity before inference

How to catch corrupted or inconsistent input early, before it shapes a conclusion.

Why this matters beyond markets

Any analysis that selects among many models, relies on simulation or ingests raw instrument output faces these same questions. I want to learn how researchers answer them on real scientific data.
